# RepoLens 创作总指南：步骤、提示词与 Git 时机

> 更新：2026-09-19。本文是后续创作的执行入口。当前已完成 M0、本地 Git 基线和步骤 2 的 React 演示页面；`web/` 已建立，步骤 3 收尾验收待做；尚无 `server/` 或 SQLite。
>
> 下方提示词是未来任务的模板。阅读本文不会自动执行其中的任务；选中一个步骤，把该步提示词发送给 Codex，再检查交付结果。命令说明见 [Git 操作手册](04-git-workflow.md)。

## 如何使用这些文档

| 你现在想做什么 | 打开哪份文件 |
|---|---|
| 知道下一步、复制提示词、确认完成条件 | 本文件 |
| 知道页面和用户流程是什么 | [01 产品蓝图](01-product-blueprint.md) |
| 看整体阶段和当前进度 | [02 里程碑与进度](02-delivery-roadmap.md) |
| 看前端、后台、数据库和文件怎样配合 | [03 系统架构与数据保存](03-system-architecture-and-storage.md) |
| 初始化仓库、建立分支、提交、合并或上传 | [04 Git 操作手册](04-git-workflow.md) |
| 打开当前页面 / 看最初样稿 | [README 启动说明](../README.md) / [M0 视觉稿](mockups/01-workbench-concept.html) |

每次在 Codex 打开当前 `RepoLens/` 文件夹。提示词中的路径都相对于这个根目录。你可以让 Codex 执行命令，不必自己在终端输入一遍；手册中的命令用来说明实际操作，也可供你手动执行。两种方式选一种，避免重复初始化或重复提交。

本指南里的提示词用于指导开发。以后产品内部解释文件夹的模型提示词，会作为代码放在 `server/app/prompts/`，在 M3 开发时实现并版本管理。

## 全程顺序

| 顺序 | 阶段 | 本次要交付什么 | Git 时机 |
|---|---|---|---|
| 0 | M0 | 确定要实现的视觉稿 | 已选用 v0.2；后续修改按 G5 |
| 1 | M1 前置 | 保存规划基线，建立版本管理 | G0：已在本地 main 完成 |
| 2 | M1 开发 | 已创建 `web/`，开发检查通过 | 已在 `feat/m1-web` 保存；待步骤 3 收尾 |
| 3 | M1 验收 | 页面状态和视觉验收通过 | G2：有改动才提交；G3：合并 M1 |
| 4 | M2 基础 | 创建 `server/`、SQLite 和数据接口 | G1：建 M2 分支；G2：提交 |
| 5 | M2 联调 | 真实文件树、证据卡和持久化接上页面 | G2：提交；G3：合并 M2 |
| 6 | M3 开发 | 后台任务和 PocketFlow 适配接入页面 | G1：建 M3 分支；G2：提交 |
| 7 | M3 实跑 | 一次小样本真实生成，结果可回读 | G2：提交；G3：合并 M3 |
| 8 | M4 | 公开 GitHub URL 导入和版本缓存 | G1 → G2 → G3 |
| 9 | M5 | 可登记、可停止的项目操作 | G1 → G2 → G3 |
| 10 | M6 | 本地交付、用户试用、反馈迭代 | G1 → G2 → G3 |
| 11 | 可选发布 | 上传 GitHub；另行选择是否部署网页 | G4：用户选择远程仓库后才 push |

M3 是第一个在本机可以实际使用的版本。M4 接通 URL 主入口，M5 扩展运行能力，M6 验证其他人能否独立使用。GitHub 上传和网页部署是两件事；本地开发与提交都不依赖它们。

## 步骤 0：确定视觉方向（M0）

打开样稿，先看输入页和工作台。重点确认配色、三栏比例、文件夹解释是否容易读，以及运行窗口是否容易找到。样稿可继续修改，不把当前风格视为已经获得你的最终认可。

**位置：**`docs/mockups/`、`docs/01-product-blueprint.md`。本步完成后冻结一个用于 M1 的视觉版本。

**复制给 Codex：**

```text
请先阅读 docs/00-creation-guide.md 的步骤 0，以及 01 产品蓝图和现有视觉样稿。
本次完善 M0 视觉设计：保留“集中输入 → 文件夹地图 + 解释区 + 固定运行窗口”的流程。
结合我在这条消息补充的审美意见调整布局、配色、字体和信息密度；若没有补充，沿用当前浅色青绿色方案。
交付可打开的 HTML 设计稿和输入页、工作台截图，明确标注演示状态。
检查桌面与窄屏显示，在 docs/02-delivery-roadmap.md 记录本次结果和待确认事项。
只完成本步。最终告诉我打开哪个文件、哪些视觉决定需要我看一下。
```

**验收：**两个页面可查看，主要内容不重叠；真假数据边界清楚。若你已认可现有样稿，本步直接跳过。

**Git：**M0 样稿已纳入步骤 1 的本地基线。若以后回来调整样稿，按 G5 的日常修改流程记录。

## 步骤 1：建立 RepoLens 的 Git 基线

**位置：**根目录 `.gitignore`、`.git/`、现有 README、`docs/`、`notes/`。这一步保存已有成果，还不会创建应用。

**复制给 Codex：**

```text
请按 docs/00-creation-guide.md 的步骤 1 和 docs/04-git-workflow.md 的 G0 操作。
在当前 RepoLens 根目录建立本地 Git 版本管理。先检查是否已经有仓库及已有改动，避免重复初始化。
创建或合并 .gitignore，忽略 upstream、var、依赖、构建产物、虚拟环境与密钥，允许 .env.example 作为无密钥模板被记录。
检查提交身份；如果缺少姓名或邮箱，只向我询问真实值，不代填身份。
检查将要提交的文件，只提交当前规划和研究资料，建立 main 分支上的基线提交。
更新路线图状态后再提交。给我提交编号和纳入版本管理的目录；本次只保存到本机。
```

**验收：**Git 根目录就是 RepoLens，初始提交存在，`upstream/` 和 `var/` 被忽略。

**Git：**执行 G0。初始化只做一次。

## 步骤 2：把视觉稿变成 React 页面（M1 开发）

**前提：**步骤 1 已完成，有一版可沿用的视觉稿。

**位置：**新建 `web/`；页面在 `web/src/pages/`，组件在 `web/src/components/`，演示数据在 `web/src/demo/`。

**复制给 Codex：**

```text
请阅读 docs/00-creation-guide.md 的步骤 2、01 产品蓝图及选定的 docs/mockups/ 视觉稿。
开始 M1：按 Git 手册 G1 创建或恢复 feat/m1-web，在根目录建立 web/。
使用 React、TypeScript、Vite 实现输入页和三栏工作台；核对本机环境与依赖要求，安装前端依赖并保存锁文件。
支持示例入口、文件夹选择、详情切换、表单修改和结果页切换。
用明确标记的演示数据覆盖空状态、处理中、成功、失败；演示运行不得声称调用了真实模型。
代码按页面、组件、演示数据拆分；保留样稿的视觉层次。README 写明启动目录、命令和本地地址。
完成构建检查和浏览器关键路径检查，更新路线图；按 G2 提交本步相关文件，先保留在 M1 分支。
```

**验收：**页面可以启动；点击会改变内容；浏览器和构建无阻塞错误；演示状态可辨认。

**Git：**G1 创建 `feat/m1-web`；G2 保存开发提交。此时先不合并。

## 步骤 3：完成页面验收（M1 收尾）

**位置：**`web/`、`evidence/m1/`、路线图。页面启动命令以步骤 2 写进 README 的实际命令为准。

**复制给 Codex：**

```text
请按 docs/00-creation-guide.md 的步骤 3 验收当前 M1，在已有 feat/m1-web 分支继续。
按 README 启动页面，走通“输入页 → 示例项目 → 选择文件夹 → 操作表单 → 演示结果”。
检查空状态、处理中、成功、失败，以及桌面和窄屏布局；修复阻塞问题。
把实际截图和验收结果写入 evidence/m1/acceptance.md，不把样稿截图当成实现验收。
记录测试命令、结果、剩余问题，更新路线图和 README。
有修改时按 G2 提交；验收通过后按 G3 将 M1 合并到 main。若有阻塞，保留分支并说明原因。
本步结束，不继续接后台。
```

**验收：**可以稳定演示页面交互，有真实截图和检查记录。

**Git：**G2 提交验收改动；G3 合并 `feat/m1-web`。

## 步骤 4：建立后台与数据保存（M2 基础）

**位置：**新建 `server/` 和 `var/`；数据库结构与迁移文件放 `server/`，实际数据库放 `var/repolens.sqlite3`。

**复制给 Codex：**

```text
请阅读 docs/00-creation-guide.md 的步骤 4 和 03 系统架构与数据保存方案。
按 G1 创建或恢复 feat/m2-repository-map，建立 Python FastAPI 后台和独立虚拟环境。
接入 SQLite，建立项目、快照、文件夹卡、证据引用的数据结构与可重复执行的迁移机制。
数据库代码进入 server/；数据库文件、快照和运行数据进入被忽略的 var/。
实现健康检查、项目列表和项目详情接口；写明请求与响应字段，供前端接入。
增加持久化和迁移验证：重启后台后仍能读回项目，重复迁移不会破坏已有记录。
记录 Python 版本、依赖、启动及验证命令，更新 README 和路线图，按 G2 提交。
本步先完成后台与保存基础，保留 M2 分支供下一步联调。
```

**验收：**后台可启动；数据真实写入 SQLite；重启后可读回；数据库和虚拟环境不进入 Git。

**Git：**G1 创建 `feat/m2-repository-map`；G2 保存基础提交。

## 步骤 5：把真实仓库接到页面（M2 联调）

**位置：**`server/` 的导入和扫描模块、`web/` 的 API 客户端、`evidence/m2/`。

**复制给 Codex：**

```text
继续 docs/00-creation-guide.md 的步骤 5，在 feat/m2-repository-map 上联调。
先让后台只读扫描已下载的 PocketFlow 样本；再支持浏览器选择目录并上传文件及相对路径。
按架构文档建立快照和 SQLite 记录，处理文件大小、总量、路径越界与应排除文件。
前端用真实接口数据替换项目地图的演示数据；保留演示模式标签供对比。
职责说明关联具体文件与源码位置，区分事实和推断；无依据的内容标为待核实。
验收：刷新和重启后项目仍在，main.py、flow.py、nodes.py、utils 的线索可核对；空目录、非法路径和过大文件有明确状态。
记录 evidence/m2/acceptance.md，更新文档，按 G2 提交。通过后按 G3 合并 M2 到 main。
```

**验收：**页面显示真实目录；项目可再次打开；证据与来源快照一致。

**Git：**G2 提交联调改动；G3 合并 `feat/m2-repository-map`。

## 步骤 6：接入运行任务（M3 开发）

**位置：**`server/` 的任务服务、PocketFlow 适配器、`server/app/prompts/`；`web/` 的运行窗口；运行数据放 `var/runs/`。

**复制给 Codex：**

```text
请按 docs/00-creation-guide.md 的步骤 6，创建或恢复 feat/m3-pocketflow-runner。
先核对本地 PocketFlow 的来源、Commit、许可证、依赖及入口。在隔离的虚拟环境准备所需依赖，保留上游快照。
实现任务创建、阶段状态、日志读取、取消、完成和失败；运行记录写入 SQLite，产物放 var/runs/。
通过受控参数数组调用固定 PocketFlow 入口，分析对象来自已经登记的项目快照。
接入页面表单、状态轮询、Markdown 预览和产物链接；渲染生成内容时禁用可执行 HTML。
把补充文件夹职责的模型提示词放入 server/app/prompts/ 并版本管理；引用不匹配时标待核实。
本步使用替身进程或固定输出验证成功、失败、取消和后台重启，不发送真实模型请求。
更新实际配置说明、启动方法和路线图，按 G2 提交；真实运行留给步骤 7。
```

**验收：**任务流程可联调；失败/取消不会变成成功；后台重启后遗留任务有明确的中断状态。

**Git：**G1 创建 `feat/m3-pocketflow-runner`；G2 保存开发提交。

## 步骤 7：真实跑通一次（M3 验收）

**前提：**模型服务、模型名称和可用密钥已确定；用户在本机配置密钥。缺失时先说明具体缺少哪项，不在聊天里索要密钥明文。

**复制给 Codex：**

```text
继续 docs/00-creation-guide.md 的步骤 7，在 feat/m3-pocketflow-runner 验收真实流程。
先检查后台模型配置是否齐全，只报告配置状态，不显示密钥。
配置齐全后，允许启动一次小样本真实模型任务：只分析 PocketFlow 的 utils 范围，中文，最多 3 个核心主题。
用页面完成启动、查看阶段日志、打开 Markdown 结果；遇到持续报错先定位，避免反复重跑消耗额度。
核对数据库任务记录、输出文件和页面预览一致；检查缺少密钥、执行失败、取消与重新打开历史结果。
真实结果和验收说明放 evidence/m3/，原始运行数据留 var/；记录实际模型和来源 Commit。
修复问题、更新 README 和路线图，按 G2 提交；真实流程通过后按 G3 合并 M3。
若配置仍缺失，只记录已完成的验证和阻塞点，不把 M3 标记完成。
```

**验收：**用户通过页面得到真实教程，并能再次打开结果；没有把模拟结果写成运行验证。

**Git：**G2 提交代码与筛选后的验收证据；G3 合并 `feat/m3-pocketflow-runner`。数据库、原始输出和密钥不提交。

## 步骤 8：接入公开 GitHub URL（M4）

**位置：**后台远程导入器、`web/` 的 URL 入口、`var/snapshots/`、`evidence/m4/`。

**复制给 Codex：**

```text
请按 docs/00-creation-guide.md 的步骤 8，创建或恢复 feat/m4-github-import。
让首页接收公开 GitHub 仓库 URL，解析并固定 Commit，再读取该版本的快照进入现有导入流程。
用本项目已选择的 PocketFlow 官方仓库做远程验证样本；设定大小、文件数、超时限制，校验解包后的路径范围。
按仓库和 Commit 复用快照，区分源码快照缓存与模型结果缓存；同一个 Commit 的不同模型或参数不能混用结果。
页面展示真实版本、读取进度、错误状态和最终地图；扫描内容与运行分析使用同一快照。
验证错误 URL、不存在仓库、限流、重复导入和版本变化，记录 evidence/m4/acceptance.md。
更新文档，按 G2 提交；通过后按 G3 合并 M4。远程导入不会执行仓库里的代码。
```

**验收：**URL 导入真实可用；来源版本一致；重复导入不会无限产生副本。

**Git：**G1 → G2 → G3，分支为 `feat/m4-github-import`。应用下载源码与向自己的 GitHub 仓库 push 是不同动作。

## 步骤 9：把运行能力做成已登记操作（M5）

**位置：**`server/app/recipes/`、隔离运行模块、前端操作表单、`evidence/m5/`。

**复制给 Codex：**

```text
请按 docs/00-creation-guide.md 的步骤 9，创建或恢复 feat/m5-action-recipes。
以 M3 已验证的 PocketFlow 教程生成入口作为第一份真实运行配方，先把现有能力登记化。
每份配方明确入口、依赖环境、参数类型、工作目录、超时、停止方式和产物；前端从配方生成表单。
登记的执行入口与被分析的仓库快照分开处理；普通上传文件不能直接变成可执行入口。
为扩展目标项目执行建立隔离运行方案，验证文件访问范围、停止时子进程退出、超时和退出码。
给出新增一个配方的开发操作说明；测试夹具仅证明运行器行为，不能充当真实第三方项目已支持的证据。
记录 evidence/m5/acceptance.md、更新文档，按 G2 提交；通过后按 G3 合并 M5。
```

**验收：**至少 PocketFlow 配方可操作；新增项目接入方式明确；取消、失败和产物定位可验证。新增其他真实项目需先明确目标和入口，再扩展配方。

**Git：**G1 → G2 → G3，分支为 `feat/m5-action-recipes`。

## 步骤 10：交付与真实试用（M6）

**位置：**本地启动工具 `scripts/`、`docs/05-local-setup-and-trial.md`、`evidence/m6/`。这些路径到本步才建立。

**复制给 Codex：**

```text
请按 docs/00-creation-guide.md 的步骤 10，创建或恢复 feat/m6-local-delivery。
把当前产品整理成本地可交付版本，写出从首次安装到启动、停止、配置密钥、备份和恢复数据的操作说明。
为当前 macOS 环境提供可双击的启动入口，检查依赖后启动前后台，输出可理解的报错；后台默认仅监听本机。
保证从 Git 检出后能根据固定来源和 Commit 准备 PocketFlow；upstream 没被提交不能成为遗漏安装步骤的理由。
备份方案覆盖 SQLite 的一致性快照及引用文件，验证一次恢复后能打开项目和历史结果。
设计 3 个用户任务：找出文件夹用途、从页面完成一次运行、找到解释的源码依据；准备观察记录模板。
完成安装和关键流程验收，写 docs/05-local-setup-and-trial.md，更新 README，按 G2 提交；技术交付通过后按 G3 合并。
把“技术交付通过”和“3 位真实用户试用完成”分别记录，尚无真实反馈时保持后者未完成。
```

**收到真实试用记录后再复制：**

```text
请阅读 RepoLens 的创作指南、M6 试用文档和我提供的真实观察记录。
提取阻塞用户完成任务的问题，按影响排序，选择一个可验证的问题修复。
按 Git 手册 G5 创建修复分支，完成修改、验证和前后对比记录。
只依据实际记录填写用户结果；缺失样本数或反馈明确保留为空。
有证据表明问题已修复后提交并合并，更新 M6 进度；本次只完成这一轮迭代。
```

**验收：**能够按文档启动与恢复数据；至少 3 位目标用户的真实记录和一次反馈迭代是 M6 全部完成的条件。

**Git：**技术交付用 G1 → G2 → G3；之后每轮改进用 G5。

## 每一步结束后保留什么

Codex 应更新 [02 进度表](02-delivery-roadmap.md)，在相应 `evidence/mN/acceptance.md` 记录验收（从实际功能验收开始）。记录至少包含：日期、对应步骤、实现内容、测试命令和结果、截图或产物位置、剩余问题、下一步。已有代码的验收可记录测试时的 Commit；包含该验收文件的提交编号在提交后回报，不要求文件记录自身提交编号。

Git 提交说明阶段性改动已保存；是否验收通过由证据决定。一个阶段未通过，可以在同一分支继续修改和提交；通过后再合并 main。
