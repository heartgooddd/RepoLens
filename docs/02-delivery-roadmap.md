**代码位置：**已有 `web/src/pages/` 放输入页和项目页，`web/src/components/` 放文件夹地图、说明卡和运行窗口。已有 `server/app/` 放 API、模型和保存层，`server/tests/` 放接口和持久化测试；已添加仓库扫描、PocketFlow 固定真实入口与替身运行任务。产品代码不写入 `upstream/`。

## 3. 每一步的具体工作

### M0：方案文件（已确认）

1. 用 `docs/01-product-blueprint.md` 检查页面与两种运行动作是否符合目标。
2. 用本文件确认目录分工、里程碑和每一步的验收标准。
3. Git 基线已按创作指南步骤 1 保存；下一步从步骤 2 开始 M1。

### M1：页面骨架

1. 确认创作指南步骤 1 已建立 Git 基线，再创建或恢复 M1 开发分支；规则与命令以 Git 手册为准。
2. 在根目录建立 `web/`，使用 React + TypeScript + Vite；在 `web/src/` 分开输入页、文件夹地图、详情卡和运行面板。
3. 为 PocketFlow 制作明确标为“演示数据”的本地样本；点击文件夹会更新中间说明，点击操作会更新右侧表单。
4. 做好空状态、处理中、成功、失败四种页面状态；运行按钮在尚无后台时显示“演示”，不展示虚假的完成结果。
5. 用桌面宽度和窄屏各检查一次；保存可回看的页面截图到 `evidence/`。

### M2：真实文件夹地图

1. 在根目录建立 `server/` 和 `var/`；建立 `var/repolens.sqlite3` 的项目、快照、文件夹卡与证据表，并为 `var/`、密钥文件、前端构建产物建立忽略规则。
2. 内置 PocketFlow 样本由本机后台读取现有路径；其他本地目录由浏览器目录选择器提交文件及相对路径，后台放入 `var/` 的独立快照。浏览器不传绝对路径；过滤 `.git`、密钥文件、依赖与构建目录，并限制总量、单文件大小和路径穿越。
3. 后台读取文件树、README、配置与可能的入口文件；API 返回项目、文件夹、文件、证据的结构化数据，前端替换 M1 演示数据。内置样本记录 Commit，上传目录记录快照标识。
4. 从 README、配置文件、文件名与入口关系提取可核对的线索，再给文件夹职责卡；证据不足时写“待核实”，不根据目录名编造功能。
5. 用 `upstream/pocketflow-codebase-knowledge/` 验收：能指出 `main.py` 的入口、`flow.py` 的流程连接、`nodes.py` 的节点实现和 `utils/` 的辅助代码；点击说明能返回源文件位置。

### M3：接入 PocketFlow 生成流程

1. 后台把页面表单映射为 `main.py` 的 `--dir` / `--repo`、`--language`、`--max-abstractions`、`--output` 等参数，以参数数组启动，不拼接用户输入的 shell 命令。
2. 运行任务把开始时间、来源、参数、状态和产物索引写入 SQLite，原始日志与 Markdown 写入 `var/runs/`。密钥留在后台环境；页面只显示“已配置 / 未配置”。
3. 利用后台模型能力补齐需要推断的文件夹职责，每条说明保存引用的具体文件；与 M2 的源码事实分开显示。
4. 前端每隔短时间读取任务状态，根据后台日志显示六个阶段的当前进度、可停止操作和失败原因；任务完成后预览 `index.md` 及章节。
5. 先用小目录做真实运行验收，核对输出文件和页面预览一致；同时验证缺少密钥、无效目录、任务失败三条路径。

### M4：公开 GitHub 仓库导入

1. 接通输入页的 GitHub URL；只接受明确的公开仓库 URL，固定读取时的 Commit。
2. 后台对下载大小、文件数和扫描时间设限，把快照放入 `var/`，对相同 Commit 复用结果。
3. 文件夹卡、证据和运行记录统一展示该 Commit；远程仓库默认只读。

### M5：已登记的项目操作

1. 将 M3 已验证的 PocketFlow 入口登记为首份运行配方：操作名称、入口、参数类型、依赖、工作目录、超时、输出与停止方法。其他真实项目明确目标与入口后再扩展。
2. 后台只允许调用登记过的配方；把目标项目放在隔离环境中运行，记录日志、退出码和产物。
3. 页面使用与 M3 相同的固定运行窗口，展示参数、执行状态、停止和结果。先验证一个操作，再增加别的项目。

### M6：试用与交付

1. 准备无需读源码即可启动的本地安装说明；对外试用时使用 GitHub URL 或用户主动选择上传的目录快照。浏览器网页不会直接获得用户电脑中任意文件夹的路径。
2. 找至少 3 位目标用户，观察他们是否能找到文件夹职责、入口、运行结果和证据；记录失败点和耗时。
3. 修复最主要的阻塞点，保存前后对比和可复查的验收记录，再决定公开部署范围。

## 4. 技术边界与验收记录

- 计划技术组合：`web/` 用 React + TypeScript + Vite，`server/` 用 Python FastAPI，与现有 Python PocketFlow 入口相接。库版本在实际初始化时按官方文档核对并锁定。
- 数据最小单元：项目来源与 Commit、文件夹卡、证据、可运行操作、运行记录。不要把模型生成的结论覆盖原始源码事实。
- 第一次代码实施只做 M1；达到验收后再做 M2。每一阶段都应能独立演示，不把未接通的按钮包装成可用功能。
- 每次验收在 `evidence/` 留下简短记录：使用的 Commit、操作步骤、预期与实际结果、截图或产物路径、未解决问题。真实运行前单独配置 API Key，不把密钥写进文档或提交。
