# RepoLens 产品与页面蓝图

> 状态：M1–M5 已实现（2026-09-22）。本文件保留产品目标；实际远程导入边界见 [M4说明](09-github-import.md)，已登记操作见 [M5说明](10-action-recipes.md)。

数据保存、前后端职责和页面视觉样稿见[系统架构与数据保存方案](03-system-architecture-and-storage.md)。

开始实施请使用 [00 创作总指南](00-creation-guide.md)中对应阶段的提示词；Git 命令集中在 [04 Git 操作手册](04-git-workflow.md)。本文件维护产品目标与页面设计。

## 1. 产品要帮用户完成什么

目标用户是想理解和使用开源 AI 项目、但不熟悉代码仓库的 AI 产品经理和初级开发者。一次使用应能依次回答：

1. 这个项目总体能做什么？
2. 各个主要文件夹承担什么职责？
3. 想使用某项功能，应从哪个入口开始、需要准备哪些参数？
4. 点击运行后发生了什么，结果在哪里，失败时卡在哪一步？
5. 哪些解释来自源码，哪些是模型推断，哪些经过实际运行验证？

第一条完整体验以本地 `upstream/pocketflow-codebase-knowledge/` 为样本。其现有程序通过 `main.py` 接收仓库地址或本地目录，串联六个节点并输出 Markdown 教程；“文件夹职责地图”和图形操作页面是 RepoLens 要新建的能力。

## 2. 页面顺序

### 页面 A：输入项目

参考 [GitDiagram](https://gitdiagram.com/) 的简洁入口：页面中央只有一句价值说明、GitHub URL 输入框、选择本地文件夹入口和一个明确的“开始了解项目”按钮。下方显示一个已经准备好的 PocketFlow 示例，用户可以直接进入。每个输入方式只有在后台能力接通后才显示为可用。本地文件夹由浏览器选择并上传文件快照；已准备好的 PocketFlow 示例由本机后台直接读取。

### 页面 B：项目工作台

```text
┌───────────────────────────────────────────────────────────────────────────┐
│ 项目名 / 来源 / Commit                         搜索文件夹     历史运行 │
├───────────────────┬──────────────────────────────┬────────────────────────┤
│ 文件夹地图        │ 当前选中的文件夹或功能       │ 固定操作窗口           │
│                   │                              │                        │
│ ▸ 根目录          │ 主要作用                     │ 可用操作               │
│   ▸ utils/        │ 关键文件与入口               │ ○ 生成项目导览         │
│   ▸ docs/         │ 输入 → 处理 → 输出            │ ○ 运行已登记的示例     │
│   ▸ ...           │ 源码依据 / 判断类型          │                        │
│                   │ 推荐下一步阅读路径           │ 参数表单               │
│                   │                              │ [开始运行] [停止]      │
│                   │                              │ 进度 / 日志 / 结果链接  │
└───────────────────┴──────────────────────────────┴────────────────────────┘
```

左侧先展示文件夹和职责摘要，再逐层展开文件；中间解释当前选择；右侧始终保留操作窗口。窄屏时右侧改为可打开的面板，保持同一操作顺序。

**文件夹卡片固定字段：**路径、一句话职责、重要文件、可用操作、证据位置、结论类型。`源码事实`、`模型推断`、`运行验证`分别标记；缺少依据的职责说明显示“待核实”，不伪装成确定事实。点击证据可定位到文件和行号；GitHub 来源记录 Commit，本地上传记录快照标识。

### 页面 C：运行结果

运行窗口按“准备环境 → 启动 → 处理中 → 完成 / 失败 / 已停止”显示状态。完成后在同页预览 Markdown 结果，提供原始文件路径、运行参数和日志；失败时展示失败阶段和下一步可操作的提示。用户可以返回文件夹地图继续浏览。

## 3. 两种“运行”动作

| 动作 | 页面呈现 | 后台实际做什么 | 首次交付阶段 |
|---|---|---|---|
| 生成项目导览 | 选择来源和语言，点击“生成” | 调用已有 PocketFlow `main.py`，读取 Markdown 产物 | 第一个可用版本 |
| 运行目标仓库功能 | 选择已登记的具体操作，填写参数后点击“运行” | 按该项目的运行配方准备环境并执行指定入口 | 后续扩展 |

目标仓库中的普通文件不自动变成“运行”按钮。一个可运行操作必须明确入口、参数、依赖、工作目录、预期产物和停止方式；界面只列出已经登记并验证的操作。这样用户不需要输入终端命令，同时能看清点击按钮会启动什么。

## 4. 页面背后的数据流

```mermaid
flowchart LR
  A[选择本地目录或输入 GitHub URL] --> B[读取文件树与记录来源版本]
  B --> C[生成文件夹地图与证据卡]
  C --> D[用户选择操作和填写参数]
  D --> E[后台创建运行任务]
  E --> F[执行 PocketFlow 或已登记的项目操作]
  F --> G[保存日志与产物]
  G --> H[页面显示进度、结果和源码依据]
```

首个实现建议用 [Vite 的 React + TypeScript 模板](https://vite.dev/guide/)构建 `web/`，用 [FastAPI](https://fastapi.tiangolo.com/tutorial/first-steps/)构建 Python `server/`。Python 后台负责扫描仓库、校验参数、启动受控任务和读取产物；前端只通过 API 触发操作。前端不持有模型密钥，也不直接执行本地脚本。

## 5. 第一版明确范围

第一版已完成“本地／公开GitHub PocketFlow样本 → 固定快照 → 文件夹地图 → 配方表单发起教程生成 → 查看运行状态与结果”的闭环。文件夹树以确定性的路径和文件索引建立，职责摘要逐条附源码依据；模型生成的解释在有证据后加入。GitHub URL 输入已在M4开放，M5已登记首份PocketFlow配方并建立macOS隔离；多人账户及公开托管需要后续单独确定范围。

**首次验收路径：**用户打开页面，选择已经下载的 PocketFlow 示例，能看懂主要文件夹及入口；在右侧填入语言等参数，点击一次生成；页面显示执行状态，结束后可以打开 `index.md` 和章节，并能找到本次的来源 Commit、运行参数和日志。

## 6. 设计检查点

- 首屏只有一个主要动作；工作台里“看懂结构”和“开始运行”都始终可见。
- 同一条解释能回到具体源码或明确标为推断。
- 没有密钥时，文件夹浏览仍可使用；生成操作显示缺少的配置。
- 后台执行只接受页面提供的结构化参数和已登记操作；每次运行有独立状态、日志和输出目录。
- 示例数据与真实扫描结果在页面上明确区分。
